# 门店任务管理平台 · 系统手册

> 给后续维护者（人或 AI）看的说明书。读完这一份就能知道：系统长什么样、数据在哪、怎么改、改完怎么验、出错怎么退。

---

## 1. 系统是什么

给「纯玩世界」连锁门店用的任务与提需管理平台。

- 总部下发任务（每日/每周/每月/专项）→ 门店提交完成 → 统计与考核
- 门店提需求 → 管委会评估 → 派发给责任人 → 完成 → 门店确认归档
- 提醒通道：钉钉单聊 + 站内消息中心

技术栈：Node 18+（实际用 Node 22）+ Express + better-sqlite3 + 原生 JS SPA（无框架、无构建步骤）。

## 4. 数据模型（最重要的一节）

### 4.1 双存储结构

同一份业务数据存在**两处**：

1. `state_doc` 表：一条记录，整个系统存成一个 JSON（`id=1`，带 `version` 乐观锁）
2. 业务表：`tasks` / `demands` / `task_records` / `contacts` / `stores` / `config_kv`

**读**走业务表（`split.readState()` 拼装回原结构），**写**先落 `state_doc` 再镜像到业务表。

> ⚠️ **铁律：任何写数据库的路径，写完必须调用 `split.syncToTables(state)`。**
>
> 2026-10-30 的线上事故：`/api/record/submit` 直接 `UPDATE state_doc` 没同步，门店提交后刷新就"变回未提交"，因为页面读的是表。

### 4.2 为什么每张表都有 payload_json

业务字段经常加。`payload_json` 存完整对象，`readState()` 优先用它还原——加字段不需要改表结构、不需要迁移。

### 4.3 关键字段

| 表 | 关键字段 |
|---|---|
| `tasks` | id, title, cycle(daily/weekly/monthly/once), status, storeIds(JSON里), remindBeforeMin, remindOverdue（完整对象在 payload_json） |
| `demands` | id, code, store_id, status, assign_to, archived_at, deleted_at |
| `task_records` | id = `taskId\|storeId\|periodKey`，periodKey 形如 `2026-10-30` |
| `contacts` | id, name, dept, phone |
| `notify_log` | event_key+person_id 为联合主键，status ∈ sent/skipped/dry/pending/deferred |
| `inbox` | event_key+person_id，read_at 为空即未读 |
| `state_snapshots` | 整库快照，保留最近 60 份 |
| `change_log` | 每条数据的 before/after，保留 2000 条 |
| `audit_log` | 操作审计（谁在什么时候做了什么） |
| `ding_map` | 账号 → 钉钉 userId 映射 |

### 4.4 提需状态机

```
pending(待评估) → approved(待派发) → assigned(处理中) → completed(待确认) → confirmed(已确认)
        ↓                ↓                  ↑                ↓
    rejected(已驳回)   (可删除)          reopen(退回重做)   archived(归档)
```

删除规则：仅 `pending` / `rejected` 可软删，且只有**提出门店本人或管理员**能删。

## 6. 权限模型

`requireAuth` 解析 JWT 后产出 `req.actor`：

| 字段 | 含义 |
|---|---|
| `isStore` | 门店账号（id 即门店 id，如 ST04） |
| `isHq` | 总部账号 |
| `isCommittee` | 管委会（`hq.committee = true`） |
| `isAdmin` | 管理员（`hq.admin = true`） |

### 6.1 谁能改什么（2026-11-01 单测后收紧）

| 动作 | 允许的角色 | 说明 |
|---|---|---|
| 新建 / 修改 / 停止 / 恢复 / 删除 **任务** | 仅 `isHq`（总部） | 门店账号一律 403；重复 id 返回 409，不会静默覆盖 |
| 改 / 停 / 删 **他人发布的任务** | 发布人本人、`isAdmin`、`isCommittee` | 其他总部 403 |
| 提交 / 撤销 **任务记录** | 该任务派发的门店 | 且本期必须已生效（到期日 ≥ 生效日） |
| 提交 **需求** | 仅门店账号，且只能提本店 | 总部代提 403 |
| 评估 / 派单 / 归档 / 退回 **需求** | 管委会、管理员 | 门店自审 403 |
| 完成需求 | 该需求的责任人 | 其他人 403 |
| 确认需求 | 提出需求的门店 | 其他人 403 |
| 增删改 **通讯录** | 管委会、管理员、人事部 | 门店 403 |
| 查看 **提醒记录 / 快照 / 改动日志** | 管理员（提醒记录另含管委会） | 门店 403 |

数据可见范围：

- 门店：只看自己的任务/记录/提需
- 总部（非管委会）：只看到派给自己的提需
- 管委会/管理员：全部

**原则：权限判断在服务端做，前端只做显示控制。**

## 7. 版本管理与发布

### 7.1 Git

- 仓库：`git@github.com:Tuligeee/cwsj.git`（私有）
- 分支：只有 `main`；历史版本另有一条 `legacy` 分支放拆表前的代码
- 标签：`v1.0.0`（拆表上线）→ `v1.0.2` → `v1.0.3` → `v1.0.5` → `v1.0.6`（提醒记录）→ `v1.0.7`（权限收紧 + 月任务生效日 + 静音汇总 + 信箱改版）
- 部署密钥：服务器 `~/.ssh/cwsj_deploy`（公钥已加到仓库 Deploy keys，write 权限）

### 7.2 不进仓库的东西（`.gitignore`）

`node_modules/`、`data/`（**含数据库、jwt.secret**）、`logs/`、`backups/`、`.ding.env`（**钉钉密钥**）、`*.bak-*`、`*.db*`

### 7.3 发布命令

```bash
cd /opt/cwsj
git add -A
git -c user.name=Tuligeee -c user.email=Tuligeee@users.noreply.github.com commit -m "改了什么"
git tag -f v1.0.x
git push origin main && git push origin v1.0.x
```

### 7.4 部署与回退（脚本在 `/opt/cwsj-ops/`）

```bash
/opt/cwsj-ops/deploy.sh status          # 当前版本、服务、健康
/opt/cwsj-ops/deploy.sh list            # 所有版本
/opt/cwsj-ops/deploy.sh v1.0.5          # 部署指定版本（只换代码）
/opt/cwsj-ops/deploy.sh v1.0.5 --with-data   # 代码 + 该版本部署时点的数据
/opt/cwsj-ops/deploy.sh rollback        # 退回上一版（依据 data/deploy-history.log）
```

**为什么脚本不在仓库里**：脚本本身受版本控制时，切到没有该脚本的旧 tag 会导致它自己消失，无法再切回来。这是实测踩过的坑。

**为什么回退依据部署历史而不是 tag 时间**：`v0.9.0` 是后补提交的，按时间排序会退错版本。

每次部署会自动把当时的数据库存到 `/opt/cwsj-backups/deploy-<tag>-<时间>/`。

## 8. 钉钉提醒引擎

### 8.1 场景（16 个）

| 组 | 场景 |
|---|---|
| A 任务 | A1 新任务 · A2 临期 · A3 逾期 · A4 逾期每日催办 · A5 门店已提交 |
| B 提需 | B1 待评估 · B2 待派发 · B3 驳回 · B4 派单 · B5 待确认 · B6 已确认 · B7 退回 · B8 临近完成日 |
| C 堆积 | C1 超期未处理 · C2 评估超 24h · C3 确认超 48h |

### 8.2 运行机制

- 服务内 `setInterval` 每 **2 分钟**：`notify.scan()` 算候选 → 写 `notify_log` + `inbox` → 若 `enabled && !dry` 则 `flush()` 真发
- 去重：`(event_key, person_id)` 唯一。`event_key` 由「场景+业务对象+周期」拼成，**改 key 格式等于让历史记录失效，会重复发**（2026-10-30 踩过，27 条重复）
- 免打扰：22:00–08:00 不发送，标记 `deferred`；08:00 后放行
  - 同一人夜里只有 1 条 → 原样补发
  - 同一人夜里 ≥2 条 → **合并成一条「昨晚有 N 条提醒」汇总**（原条标记 `merged`），只占 1 条每日上限
- 本期未生效不算逾期：`到期日 < 生效日` 时，A2/A3/A4 一律不发（避免「月中发布月任务，立刻群发逾期」）
- 新建周期任务时自动顺延生效日：月任务的目标日已过 → 生效日设为下月 1 日；周任务的目标星期已过 → 设为下周该天
- 限流：每人每天最多 10 条（超出标记 `skipped`）
- 白名单：`notify_cfg.whitelist`（逗号分隔 ID）。**非空时名单外一律不发**，标记「测试白名单外」
- 记录保留：90 天自动清理

### 8.3 消息格式

```
【纯玩世界 · 门店任务管理】任务已逾期

- 任务：xxx
- 原定截止：10月25日 18:00
- 当前状态：逾期未提交

[立即补交](http://47.114.33.192/cwsj/#task=T_xxx&fill=1)
```

深链接：

- `#task=<id>` → 跳到任务并弹详情
- `#task=<id>&fill=1` → 直接弹「提交完成」填写框
- `#demand=<id>` → 跳到提需并弹详情

### 8.4 环境隔离（血的教训）

正式与测试**共用同一个钉钉机器人**（`dingxkanqx…`），所以：

- 测试环境 service 必须设 `Environment=NOTIFY_FORCE_TO=HQ17`：所有外发强制转发给指定人，物理上到不了门店
- 代码里默认值改成"实发"时，**测试环境会立刻跟着真发**——改默认值前必须确认测试环境已有隔离
- 另有 `NOTIFY_OFF=1` 硬闸：`cfg()` 直接返回关闭 + `flush()` 直接拒绝

## 9. 站内消息（inbox）

- 入口：**顶栏信箱图标**（原右侧悬浮铃铛与顶栏「提醒中心」铃铛均已下线）
- 形态：桌面从顶栏向下锚定覆盖（不挤压页面），手机为底部抽屉
- 旧实现留了 `.main{padding-right:72px}` 给悬浮球占位，会导致整页左移，已移除
- 数据来自同一批候选（`notify.scan` 同时写 `inbox`）
- 服务端 `WHERE person_id = 当前登录人` 天然隔离
- 点条目 → 标记已读 + 跳深链接
- 站内不依赖钉钉绑定（无钉钉的人也能看）

## 10. 已知坑（务必先读）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 原子接口只写 `state_doc` 不同步拆表 → 页面读不到 | 任何写路径后都调 `syncToTables` |
| 2 | 改 `event_key` 格式不迁移旧数据 → 全量重复发 | 改 key 前，把旧 key 按新格式补一份 `sent` 记录 |
| 3 | 改代码默认值（如 `dry`）影响所有环境 | 先看测试环境是否有 `NOTIFY_FORCE_TO` |
| 4 | 时区：DB 存 UTC，直接显示会慢 8 小时 | 显示时用 `new Date(iso)` 转本地（见 `fmtLocal`） |
| 5 | `API_ROOT` 变量在部分文件里不存在 | 统一用 `((window.Api && window.Api.base) \|\| '')` |
| 6 | 定时任务只 `scan` 不 `flush` | `flush` 必须显式调用，否则永远堆在 `pending` |
| 7 | 前端缓存 | 改 js/css 必须升 `index.html` 里的 `?v=` |
| 8 | 静态资源路径 | 服务端返回不带前缀，前缀一律由前端 `Api.base` 拼 |
| 9 | 自绘控件在重绘后消失 | 组件要"自愈"：DOM 变动时检查触发器是否还在 |
| 10 | 白名单只设了正式，忘了测试 | 两个环境各自独立配置，改完两边都查 |
| 11 | 「本期未生效」只在页面判断，接口不判断 → 门店能提前交 | 可见性、逾期、通知、提交接口**四处统一**用 `到期日 ≥ 生效日` |
| 12 | 写接口只做 `requireAuth`，前端不显示按钮 ≠ 后端有权限 | 每个写接口都显式判断角色；单测覆盖越权场景 |

## 11. 改动流程（每次照做）

1. **先算影响面**：这个改动会影响哪些数据、哪些人、哪个环境
2. **在测试环境改**：`/opt/cwsj-stg`，改完重启 `systemctl restart cwsj-stg`
3. **验证**：打开 `/cwsj-stg/` 实际点一遍；涉及数据就看 `JSON vs 表条数是否一致`
4. **给用户看结果**（截图/数字）
5. **确认后再上正式**：备份 → 同步文件 → 升 `?v=` → 重启 → 健康检查 → 页面验证
6. **提交 Git**：`commit` + `tag` + `push`
7. **5 分钟内复查**：发送队列、日志、有没有异常

## 12. 常见修改怎么做

**加一个任务字段**
在 `tasks` 对象上加属性（`payload_json` 自动带着走）；表单加输入；列表展示；`notify.js` 若需要用到再加。不需要改表结构。

**加一个提醒场景**
在 `notify.js` 的 `build()` 里 push 一条候选，给唯一的 `key`（含业务对象 id + 周期），写好 `title` / `body` / `hash`；前端「提醒记录」页会自动显示（`SCEN` 映射表加中文名）。

**加一个后台页签**
`view-hq.js` 的 `ADMIN_TABS` 数组加 `[key, 名称]`，分发处加 `else if (tab === key) paintXxxTab()`，再写 `paintXxxTab()` 函数。

**加一个接口**
`server.js` 里 `app.get/post(...)`，用 `requireAuth`，权限用 `req.actor.isAdmin/isCommittee/isStore` 判断；写完若改了数据要 `syncToTables`。

**改消息文案**
只改 `notify.js` 里对应场景的 `body` 数组；前缀由 `BRAND_PREFIX` 统一加，不要在 body 里重复写。

## 14. 术语

| 词 | 含义 |
|---|---|
| 周期 / periodKey | 一次任务实例的标识，日期格式 `2026-10-30` |
| 临期 | 距截止时间还有 `remindBeforeMin` 分钟 |
| 催办（A4） | 逾期后每天 09:00 再提醒一次 |
| 白名单 | 只给名单内的人发钉钉，其余拦截 |
| 预演（dry） | 只算不发，仅留记录 |
| 拆表 | `state_doc` JSON 之外，把业务数据同步进独立表 |
| 深链接 | 消息里带 `#task=xxx`，点开直达并弹窗 |
| allowed / skipped | 记录状态：已发送 / 被拦截 |
